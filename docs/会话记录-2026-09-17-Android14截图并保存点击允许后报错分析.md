## 根因分析

### ① 死线程 Handler 警告（仅 Android 14 出现的直接原因）

- `ScreenCapturer.initVirtualDisplay()`（ScreenCapturer.java L251-255）中，为满足 Android 14（API 34，UPSIDE_DOWN_CAKE）"createVirtualDisplay 前必须已注册 MediaProjection 回调"的要求，代码做了 `SDK_INT >= UPSIDE_DOWN_CAKE` 门控注册，回调 handler 用的是构造函数传入的 `mHandler`。
- 同步截屏时 `mHandler` 来自 Images.java L246：`new Handler(mScriptRuntime.loopers.getServantLooper())`，即**脚本 servant Looper**。
- ScriptRuntime.kt 退出顺序（L633-636）：先 `loopers.recycle()`（633）再 `images.releaseScreenCapturer()`（635）。`release()` 内 `mMediaProjection.stop()` 异步派发 `onStop` 到已死的 servant Looper handler → 死线程告警。
- Android 10 不走 registerCallback 门控分支 → 无此告警，故"正常"。

### ② EventBus 反注册警告（double release）

- `ScreenCapturer.finalize()`（L497-504）会再次调用 `release()`。
- `release()`（L467-491）非幂等：仅 `mMediaProjection` 置空，`mVirtualDisplay/mImageReader/mUnderUsingImage` 未置空；`EventBus.unregister` 二次调用 → 29.909s 警告（紧跟 29.908s 的 GC，即 finalize 路径触发）。

### ③ `A resource failed to call close`（LeakCanary）

- 有 Closeable（大概率 `Image`/`ImageReader`）被 GC 时未 close。
- 与 `release()` 内部顺序有关：先 `mMediaProjection.stop()` 再释放 VirtualDisplay/ImageReader（标准顺序应相反），且与异步派发存在时序竞争。

## 修复方案（已与用户确认方向，暂未动代码）

1. **核心修复（①）**：Android 14+ 的空 MediaProjection 回调改注册到主线程 Looper（永不死），并在 `release()` 中 `unregisterCallback`：

```java
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE) {
    // 仅需满足 Android 14 "createVirtualDisplay 前必须已注册回调" 的要求
    mMediaProjection.registerCallback(new MediaProjection.Callback() {}, new Handler(Looper.getMainLooper()));
}
```

2. **`release()` 幂等化（②）**：增加 `volatile boolean mReleased` 防重入；释放后各字段置 null。

3. **释放顺序调整（③）**：`release()` 内先 `mVirtualDisplay.release()` + `mImageReader.close()`，最后 `mMediaProjection.stop()`。

# 第二轮：开始修复（2026-09-17）

## 用户提问

> 开始修复

## 实施内容（仅修改 ScreenCapturer.java，共 3 处）

### 修复①：MediaProjection 回调改挂主线程 Looper + 只注册一次 + release 时反注册

- 新增字段 `mMediaProjectionCallback`（保存引用，防止 `initVirtualDisplay` 多次调用时重复注册泄漏）。
- `initVirtualDisplay()` 中 Android 14+ 的空回调注册 handler 由脚本 servant Looper 的 `mHandler` 改为 `new Handler(Looper.getMainLooper())`（主线程永不死亡，脚本退出回收 Looper 后不再产生死线程派发）。
- 新增 `import android.os.Looper`。

### 修复②：release() 幂等化

- 新增 `volatile boolean mReleased` 防重入标志：引擎退出显式释放 + `finalize()` 二次释放时，第二次调用直接返回，消除 `EventBus: Subscriber to unregister was not registered before` 告警。
- 所有资源释放后置 null（`mVirtualDisplay` / `mImageReader` / `mUnderUsingImage`）。
- `mMediaProjection.stop()` 前先 `unregisterCallback`（API 21+，minSdk 24 无兼容问题）。

### 修复③：释放顺序调整

- 原顺序：先 `mMediaProjection.stop()` 再释放 VirtualDisplay/ImageReader。
- 新顺序：`mVirtualDisplay.release()` → `mImageReader.close()` → `mUnderUsingImage.close()` → `unregisterCallback` → `mMediaProjection.stop()` → 反注册 DisplayListener → 退出回调线程 → EventBus 反注册。

未改动 ScriptRuntime.kt 退出顺序（主线程 Looper 方案已使其不再相关，保持最小改动）。

## 问题一：弹框半秒消失（原因与结论）

**实验证据**（通过 adb 触发 RunIntentActivity + 全量 logcat 复现两次）：
- 弹框 = `com.android.systemui.media.MediaProjectionPermissionActivity`，onResume → onPause 仅 ~220ms，随后 `MediaProjectionManagerService: start behavior of screen record` 直接放行，截图成功，全程无 HiTouch 触摸事件，设备无障碍服务列表为空（`enabled_accessibility_services=null`）。
- 设备 appops：`PROJECT_MEDIA: ignore`，每次请求 noteOp 被拒（rejectTime 持续更新为请求时刻），但 Honor 定制栈仍放行。
- AOSP 14 `MediaProjectionPermissionActivity.onCreate`：先调 `MediaProjectionServiceHelper.hasProjectionPermission(uid, pkg)`，为 true 即 `setResult(RESULT_OK)` 并 finish——**弹框根本不等人**。
- AutoJs6 抽屉的 `CommandBasedPermissionItemHelper` 为纯手动触发（root/Shizuku/adb 命令），不会自动改写 appop。

**结论**：与本次 APK 修复、AutoJs6 代码、无障碍服务均无关；是设备侧 `PROJECT_MEDIA` appop 处于 `ignore` 状态 + Honor MagicOS 定制放行逻辑所致（推测此前某次"拒绝"或手动 revoke 写入）。Android 10 设备无此状态故正常。

**恢复交互式弹框（可选）**：`adb shell appops set org.autojs.autojs6 PROJECT_MEDIA default`（或 Honor 设置中重置该应用权限）。

## 问题二：`A resource failed to call close` 根因定位与修复

**隔离实验**（adb 推送最小脚本逐级测试）：
- 空脚本（仅一行 toast，0.02s）→ 仍产生告警 → 泄漏在脚本运行公共路径，与截屏/保存无关，老 APK（02:06 日志）即存在。
- 仅请求截图 → 告警；请求+截屏不保存 → 告警；全流程 → 告警（均每运行一次泄漏一个资源，LeakCanary watch-GC 后 ~3-5s 触发告警）。

**根因**（两处，均已修复）：
1. `EncryptedScriptFileHeader.kt` `getHeaderFlags()`：打开 `FileInputStream(file)` 后所有返回路径均未关闭；该方法在每次文件脚本运行时被 `JavaScriptFileSource.parseExecutionMode()` 调用（加密文件头/执行模式检测）——**每次运行泄漏一个 FileInputStream（CloseGuard 告警来源）**。修复：`FileInputStream(file).use { }` 包裹。
2. `RhinoJavaScriptEngine.kt`：Rhino 的 `Context#compileReader` 字节码证实**不关闭传入的 reader**（只有 `Kit.readReader` 读取+编译+return）。两处调用均未自行关流：
   - `mInitScript`（每次引擎初始化读取 assets 中的 init 脚本，泄漏 AssetInputStream）→ 修复：`InputStreamReader(...).use { }`。
   - `doExecution`（每次运行读取脚本源，file 源为 FileReader/FileInputStream，sample 源为 AssetInputStream）→ 修复：`reader.use { context.compileReader(...) }`。
   - `JavaScriptSource.getNonNullScriptReader()` 每次返回新建 reader，关闭安全。

**验证**（修复后新 APK，进程 8630）：
- 空脚本运行后 13s 观察窗口：**零告警** ✓
- `test_cap.js`（请求+截屏+保存）运行结束后 14s：**零来自本应用的告警**（期间 logcat 中另有进程 13126 的 15 条告警，与本应用无关）✓
- 截屏功能正常（test_cap 1.182s 完成、/sdcard/test_out.png 生成；用户手动运行样例脚本亦正常 1.2s）

# 第四轮：弹框"一闪自动允许 + 每次弹不记住"专项排查（2026-09-17）

## 用户提问（指向 ScreenCaptureRequester#L170-181 / Images#L253）

> Android 14 弹框一闪默认就确认允许，直接走回调截屏，用户无操作；但下次还是会弹，不记住。Android 10 弹框一直等待用户操作，点击允许后下次记住不弹。查看问题，给出方案，用户决定是否执行。

## 关键对照实验（本轮完成）

**实验**：将 `PROJECT_MEDIA` appop 从原状态 `ignore` 临时改为 `default`，adb 触发截图脚本，抓取 SystemUI 弹框全生命周期。

**结果**：`MediaProjectionPermissionActivity` Displayed +137ms → destroy（自动关闭），脚本 1.036s 直接截屏成功——**改 `default` 后弹框依然自动放行**，与 `ignore` 下行为一致。排除 appop 因素。

**结论**：荣耀 MagicOS 8.0（Android 14）的 SystemUI 定制逻辑对该应用无条件/按定制规则自动通过媒体投影授权。应用层 `startActivityForResult` 仅正常发起请求，无法控制系统弹框停留或自动确认。

## 根因定性（两件事，都是系统/平台层面，应用代码不可控）

1. **弹框一闪自动确认**：Honor SystemUI `MediaProjectionPermissionActivity` 显示后 ~200-300ms 自动通过（AOSP 同文件仅当 `hasProjectionPermission()==true` 时自动放行；荣耀定制对 AutoJs6 的该判定恒为放行）。非 AutoJs6 bug。
2. **每次弹、不记住**：Android 14 平台隐私变更——每次创建媒体投影会话都必须用户确认，系统取消"永久记住授权"；Android 10 通过 appop 持久化所以只弹一次。这是 **Android 14 对所有应用**的通用行为（含系统录屏），非荣耀特例、非 AutoJs6 bug。
