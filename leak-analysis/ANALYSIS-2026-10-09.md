## 1. 泄漏 #1 — MCPLocalServer.INSTANCE（真实，已修）

**引用链**（来自 `heap_analysis.id=1`）：

```
GC Root: THREAD_OBJECT  (Thread 'CleanupReference')
  java.lang.Thread.contextClassLoader
  dalvik.system.PathClassLoader
    class com.ai.assistance.operit.data.mcp.MCPLocalServer
      static INSTANCE                     ← 进程级单例
  MCPLocalServer
    .pluginMetadata (StateFlow, stateIn(Eagerly))
      ... StateFlowImpl → StateFlowSlot → AtomicReference → CancellableContinuationImpl
          → DispatchedContinuation → StateFlowImpl$collect$1 → ContinuationImpl$L$0
    → MCPRepository$1$1 (FlowCollector 匿名类)
      .this$0
  MCPRepository
    .context  instance of com.ai.assistance.operit.ui.main.MainActivity  with mDestroyed = true
LEAKED: com.ai.assistance.operit.ui.main.MainActivity
```

**根因（上游同款，非移植引入）**：`MCPRepository` 在 `init` 里向进程级单例
`MCPLocalServer.pluginMetadata` 的 StateFlow 起了一个**永不取消**的收集协程：

```kotlin
init {
    loadPluginsFromMCPLocalServer()
    CoroutineScope(Dispatchers.IO + SupervisorJob()).launch {
        mcpLocalServer.pluginMetadata.collect { loadPluginsFromMCPLocalServer() }
    }
}
```

StateFlow 的 subscriber slot 会长期持有该协程**挂起时的 continuation**，进而钉住
`MCPRepository` 实例；而 `MCPRepository(private val context: Context)` 直接保存了构造时传入的
**Activity 上下文**（`ui/main/MainActivity.kt:507 MCPRepository(this)`、
`ui/main/OperitApp.kt:424 remember { MCPRepository(context) }`、`MCPConfigScreen`/`PackageManagerScreen`
的 `remember { MCPRepository(context) }`）。于是每次打开 Operit 主界面都会滞留一个已销毁的 MainActivity。

`modules/operit/.../data/mcp/MCPRepository.kt` 与上游 `autojs_ai_code/Operit` **逐字节相同**（已 diff 验证），
属上游设计缺陷。

**修复**：构造参数不再保存，属性收敛为 `context.applicationContext`。本类对 `context` 的使用仅
`getString / filesDir / cacheDir / getExternalFilesDir / contentResolver`，均无需 Activity 上下文，行为等价。
登记为 SYNC.md **D-14**（并标注需回灌上游，否则下次上游同步会覆盖）。

**残留（低危，已记录）**：收集协程本身仍未取消，每次创建 `MCPRepository` 仍会多驻留一个仅含
Application 上下文的小实例。彻底消除需给 `MCPRepository` 增加 `close()` 并接入生命周期，超出最小改动范围。

## 2. 泄漏 #2 — FloatingChatService$LocalBinder.this$0

```
GC Root: JNI_GLOBAL
  FloatingChatService$LocalBinder
    .this$0
  com.ai.assistance.operit.services.FloatingChatService   (已 onDestroy)
```

`LocalBinder` 是被 **native 全局引用**（binder 驱动）持有的 Binder 对象，LeakCanary 无法继续向 Java 层追溯。
排查了应用内所有绑定方，均**成对解绑**：

- `ui/features/chat/viewmodel/ChatViewModel` → `onCleared()` → `FloatingWindowDelegate.cleanup()`
  → `unregisterReceiver` + `disconnectFromService()` → `unbindService`；
- `core/tools/.../StandardChatManagerTool`（bind 1156 / unbind 1186、1330）；
- `services/UIDebuggerService`（bind 77 / unbind 108）。

`FloatingChatService.onDestroy()` 自身也已 `instance = null` + `binder.clearCallbacks()`。
因此无应用侧 Java 持有路径 → 判定为**框架/binder 级持有**（跨进程 binder 引用），非应用可修复。
上游同款代码（`LocalBinder` 与上游逐字节相同）。

## 3. 泄漏 #3 — AccessibilityService$IAccessibilityServiceClientWrapper.mContext

```
GC Root: JNI_GLOBAL
  android.accessibilityservice.AccessibilityService$IAccessibilityServiceClientWrapper
    .mContext
  org.autojs.autojs.core.accessibility.AccessibilityServiceUsher   (已 onDestroy)
```

`IAccessibilityServiceClientWrapper` 是 **Android 框架**在 `AccessibilityService.onBind()` 里创建并交给
system_server 的 Binder 客户端；其 `mContext` 就是服务实例。GC root 为 JNI_GLOBAL，说明是 binder 驱动
持有（跨进程），应用侧无 Java 持有路径。

应用侧静态引用已确认全部清理：
`core/accessibility/AccessibilityService.Companion.instance` 在 `onDestroy()` 里被置 null
（`AccessibilityService.kt:150-163`）；`delegates` 只存 `AccessibilityDelegate`，不含服务实例。

判定：**框架固有行为（良性）**。这是所有使用 AccessibilityService 的应用都会出现的 LeakCanary 报告。

## 4. 泄漏 #4 — TermSession$2.<Java Local>

```
GC Root: THREAD_OBJECT  (Thread 'TermSession input reader', jackpal TermSession$2)
  ...(ThreadLocal)...
  android.os.Message
    .target = android.view.AccessibilityInteractionController$PrivateHandler
      .this$0 = AccessibilityInteractionController
        .mViewRootImpl = ViewRootImpl
          .mContext = DecorContext wrapping SplashActivity with mDestroyed = true
LEAKED: org.autojs.autojs.ui.splash.SplashActivity
```

泄漏对象是 `SplashActivity`，被**消息队列里一条待处理的无障碍 Message** 经 handler 链持有。Message 派发后
即释放，属**瞬态泄漏**（LeakCanary 常见的 self-healing 误报）。

`TermSession` 位于预编译 AAR `libs/jackpal-androidterm-emulatorview-1_0_42/emulatorview-release.aar`
（无源码），不可就地修改。宿主侧 `runtime/api/Shell.java` 的 TermSession 生命周期是完整的：
`init()` 创建 → `exit()` 调 `mTermSession.finish()`，且 `ScriptRuntime` 在销毁时 `recycleShell()`。
判定：**瞬态 + 第三方 AAR**，不改。

## 5. 泄漏 #5 — WindowManagerGlobal.sDefaultWindowManager

`android.view.WindowManagerGlobal.sDefaultWindowManager` 是框架静态字段，持有最近一个
`ViewRootImpl → mView`（FrameLayout）。LeakCanary 自身已把该对象标为 `NOT_LEAKING`
（reason: "View is part of a window view hierarchy / View.mAttachInfo is not null"）。
判定：**已知框架静态字段（良性）**，非应用可修复。

## 7.5 修复真机验证（2026-10-09 01:50–01:56）

修复后重装 debug APK，用脚本（`leak-analysis/leaktest.js`，经 exported 的 `RunIntentActivity` 在应用进程内运行）
以同 uid 启动 Operit `ui.main.MainActivity`（该 Activity `exported=false`，`adb shell am start` / `run-as am start`
均被 SecurityException 拒绝），再双击返回键（其 `setupBackPressHandler` 是**双击退出**语义）销毁它。

**证据 1（LeakCanary）**：清库后触发，`heap_analysis` 新增一条 `leak_count = 0` 的分析，`leak` 表为空。
修复前同一路径会产出 `MCPLocalServer.INSTANCE` 泄漏。

**证据 2（离线 hprof，决定性）**：`adb shell am dumpheap com.xiaoyu.ai`（251MB hprof）→ `hprof_analyzer.py`：
- `KeyedWeakReference: 2 watched, 0 reachable`（0 个仍可达）；
- 组件销毁状态：`com.ai.assistance.operit.ui.main.MainActivity  mDestroyed=True: 1 个, 其中 0 个仍可达`
  → **已销毁的 Operit MainActivity 不再可达，泄漏消除**；
- 唯一 "已销毁但可达" 是 `org.autojs.autojs.ui.splash.SplashActivity`，路径为
  `JNI_MONITOR → SharedPreferencesImpl$1 → MemoryCommitResult.listeners → ... → AbstractAutoJs$registerActivityLifecycleCallbacks$1 lambda`
  —— 即技能文档中已记录的**良性瞬态**（SharedPreferences 提交时监听器快照被 QueuedWork 待写队列临时持有，
  自愈、LeakCanary 默认排除），不作为泄漏修复。

## 8. 结论

5 条 LeakCanary 泄漏中，**1 条是真实且可修的应用侧泄漏（#1，已修）**；其余 4 条分别是框架级 binder 持有
（#2/#3）、瞬态消息持有（#4）、框架静态字段（#5），均无应用侧 Java 持有路径可改。
